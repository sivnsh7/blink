# BLINK — Deep UI/UX, Design-System, Accessibility, Telemetry & Backend Audit

**Project:** Blink / Field Dossier — Linux Host Telemetry  
**Reviewed archive:** `BLINK-REDESIGN.zip`  
**Review date:** 1 November 2026  
**Review type:** Static source audit + available test execution + external standards review  
**Frameworks applied:** UI/UX Pro Max review model, Vercel Web Interface Guidelines, WCAG 2.2, W3C Pause/Stop/Hide, MDN reduced-motion guidance, Linux kernel PSI/procfs documentation, and Linux `random(7)` guidance.

> **Executive verdict:** Blink has a distinctive and coherent visual idea, but the current implementation is not yet a trustworthy host-monitoring product. Its largest problems are not merely cosmetic: some displayed security states are fabricated defaults, some labels misrepresent the underlying Linux metrics, storage roll-ups can double-count devices, redaction is not privacy-safe, and repeated synchronous collectors can block the API event loop. Treat this build as an experimental prototype, not a security assessment tool or production host agent.

**Overall readiness: 4.2/10.** This is a qualitative engineering judgment, not a formal score generated by UI/UX Pro Max. The project has a strong visual foundation; data truthfulness and interaction reliability need to be repaired before visual polish is considered complete.

### What is genuinely good

- The project uses one custom SVG icon set rather than a random mix of icon packs and emoji (`client/src/components/Icon.jsx`).
- The palette, typography and elevation tokens are centralized in `client/src/tokens.css`.
- Bricolage Grotesque, Space Grotesk and IBM Plex Mono are explicitly imported in `client/src/main.jsx` and fit the editorial/technical identity.
- The backend reads actual Linux interfaces (`/proc`, `/sys`, PSI) rather than relying entirely on browser approximations.
- The backend defaults to `127.0.0.1`, disables Express' `x-powered-by`, sets several useful response headers, uses an exact WebSocket origin allowlist when an Origin header exists, and caps slow-client WebSocket buffering (`server/index.js`).
- The process list is explicitly capped at 100 records, rather than returning an unlimited process table (`server/metrics.js:476–512`).
- `bytes()` consistently uses IEC binary units (`B`, `KiB`, `MiB`, `GiB`) rather than mixing GB/GiB (`client/src/lib/format.js:8–18`).
- The hero interaction checks `prefers-reduced-motion` and fine-pointer capability before enabling its pointer effects (`DossierHeroTitle.jsx:18–22`).

### Main release blockers

1. Never show `CONFIRMED SECURE`, `HARDENED`, a 95/100 security score or `256 BITS` when the audit data is unavailable.
2. A per-item reveal must never override the global masking state. The current masking is visual only, not data confidentiality.
3. Export must not silently dump raw host/process/network data when the dashboard is in masked mode.
4. Correct memory, CPU, PSI, GPU, process and storage labels so they describe the values actually collected.
5. Stop doing expensive synchronous `/proc` scans and shell commands on every telemetry sample; stop `/api/audit` from independently mutating collector baselines.
6. Fix browser Back/Forward, reconnect controls, mobile drawer semantics and modal keyboard handling.
7. Complete clean dependency installation and production build, then add meaningful backend and browser tests.

## 3. Product and interaction model

Blink is a **local Linux host telemetry dossier**. It is not an endpoint protection suite, threat-detection platform, vulnerability scanner or cryptographic certification tool. The interface should consistently communicate four different categories:

1. **Observed telemetry:** values read from Linux counters or sysfs/procfs.
2. **Derived indicators:** calculated CPU usage, memory used estimate, rates and PSI averages.
3. **Heuristic assessments:** an explicitly heuristic score with visible rules and coverage.
4. **Unavailable/unsupported data:** missing kernel support, missing driver, permission restrictions, no sensor device or collection error.

The current interface frequently blends these categories. For example, absent PSI is presented as `NOMINAL`, absent entropy becomes `256 BITS`, absent ASLR becomes level 2, and the default audit state becomes `CONFIRMED SECURE`. This is a fundamental product-trust defect.

### Recommended data-state contract

Every telemetry value should support at least these states:

- `loading`: first snapshot has not arrived.
- `available`: fresh valid value with sample timestamp.
- `stale`: a previous value exists but is older than its freshness threshold.
- `unsupported`: OS/kernel/device does not expose this metric.
- `permission-denied`: collector lacks permission.
- `error`: collector failed unexpectedly.
- `not-applicable`: metric does not apply to this host/device.

Do not coerce these states to `0`, `false`, `256`, `NOMINAL`, `BAREMETAL`, `DAC ONLY` or “no hardware”. Zero is a real observation, not a generic fallback.

## 4. P0 — Critical correctness, privacy and trust defects

### 4.1 Audit page fabricates a safe state before data exists

**Files:** `client/src/views/AuditView.jsx:31–35, 42–61, 96–123, 145–149`; `server/metrics.js:734–779, 784–848`.

Current code defaults:

```jsx
const score = audit?.score ?? 95;
const posture = audit?.postureGrade || 'CONFIRMED SECURE';
const stampClass = audit?.stampClass || 'stamp--confirmed';
```

And then uses fallbacks such as:

```jsx
{sec?.entropy || 256}
{sec?.aslr ?? 2}
```

**Why this is a blocker:** while the audit is loading, when `/api/audit` returns a non-2xx response, or when fields are missing, the user sees a high security score and positive assertions that have not been established. The entropy fallback also converts both `0` and `null` to 256. This is not simply optimistic UI; it is false security feedback.

**Required fix:**

- Initial score must be `—` or a skeleton, not 95.
- Initial posture must be `Awaiting host data` or `Audit unavailable`.
- `loading`, HTTP error, unsupported and stale must render visibly.
- Only calculate a posture after validating all required input values and their timestamps.
- Never use “confirmed secure” as a label for a heuristic score. Prefer `Heuristic posture: 82/100` with a confidence/coverage indicator and a link to the exact contributing checks.
- Remove the unconditional `HARDENED` stamp (`AuditView.jsx:71`).
- Replace `sec?.entropy || 256` with a strict numeric check, and show `—` / `Unavailable` when unknown.
- Replace `sec?.aslr ?? 2` with an explicit supported/unsupported value.

**Acceptance:** mock `/api/audit` as delayed, 404, 500, empty JSON, `null` security, entropy 0 and ASLR missing. In none of these cases may the UI claim a secure/hardened state.

### 4.2 Global redaction can be bypassed by a previously revealed item

**File:** `client/src/components/Redacted.jsx:9–45`; `client/src/context/RedactionContext.jsx:8–20`.

Current expression:

```jsx
const isRedacted = (redactionMode || force) && !revealed;
```

If a user reveals a hostname or PID, then turns global masking back on, that individual component retains `revealed === true` and continues to display the raw identifier. This contradicts the global `MASKED` status.

**Required fix:** global mask must have authority over every local reveal. Example contract:

- `effectiveMasked = force || (redactionMode && !revealed)`.
- When global mode changes to masked, clear all local reveal state or use a context-managed reveal registry that resets synchronously.
- A `force` masked value must never become revealable locally.
- Add tests for: reveal → global mask on; reveal → route change; force mask; repeated keyboard operation.

Also replace clickable `<span role="button">` with a native `<button type="button">` styled as inline redaction. The current keydown handler does not call `preventDefault()` for Space, so the page may scroll while the component is activated. The current component also lacks an explicit pressed/revealed state announcement (`aria-pressed` or a text equivalent).

### 4.3 Redaction is visual obfuscation, not confidentiality

**Files:** `Redacted.jsx:13–45`, `components.css:177–219`, `Overview.jsx:98–112`, `server/metrics.js:358–411`.

The raw text remains in the DOM; CSS changes its color to transparent and covers it with a black bar. Screen readers may still encounter the underlying text, browser extensions/devtools can inspect it, the API still returns it, and the JSON export serializes the full `metrics` object directly.

The export button in `Overview.jsx:98–112` downloads `JSON.stringify(metrics, null, 2)` without consulting `RedactionContext`. The snapshot includes identifiers such as hostnames, process names/PIDs and network interface MAC addresses (`metrics.js:358–411`). A user can therefore keep the screen visually masked and still export the raw snapshot.

**Required fix:**

- Rename the feature to `Visual masking` / `Hide host identifiers`, not “classified redaction” or security protection.
- When exporting, provide an explicit choice: `Export masked snapshot` (default) or `Export full snapshot` with confirmation.
- Construct a sanitized export object on the backend or client with allow-listed fields; do not serialize the entire live object blindly.
- Hide sensitive values from assistive technology when masked and announce that the value is hidden. Do not put raw identifiers in aria-labels while masking is on.
- Keep in mind: visual masking cannot secure data already sent to the browser. If this agent is exposed beyond loopback, access control is the primary boundary.

### 4.4 Memory labels imply the wrong Linux metric

**Files:** `server/metrics.js:129–167`; `client/src/views/Details.jsx:134–160, 180–196`; `TelemetryTicker.jsx:21`.

Backend code calculates:

```js
const used = total - available;
```

where `available` comes from `MemAvailable`. That is a useful estimate of memory pressure/used RAM, but it is not process RSS and it is not Linux `Committed_AS`.

The UI calls the same value:

- `COMMITTED / USED` (`Details.jsx:138–139`)
- `Committed RSS` (`Details.jsx:157`)
- `RAM COMMITTED` (`TelemetryTicker.jsx:21`)
- `RAM Commitment` (`Details.jsx:180`)

Those terms are not interchangeable. RSS is resident set size of processes; `Committed_AS` is the virtual memory committed by processes, including allocation that may not yet be physically touched. `MemTotal - MemAvailable` is a used-memory estimate.

**Required fix:** rename to `Estimated RAM used` or `Used estimate (MemTotal − MemAvailable)`. If the product wants true commit accounting, parse and report `Committed_AS` and `CommitLimit` separately. If it wants process RSS, sum per-process RSS with clear caveats (shared pages can be double-counted across process RSS).

### 4.5 PSI missing values become a false “NOMINAL” state

**Files:** `AuditView.jsx:47–55, 197–200, 212–227, 238–264, 276–277`; `server/metrics.js:702–730`.

When PSI files are missing or inaccessible, `parsePsiFile()` returns `null`. The frontend substitutes `0.00%` or `NOMINAL`. This incorrectly treats unsupported/disabled/permission-denied telemetry as a zero stall rate.

Linux PSI distinguishes `some` (at least some tasks stalled) from `full` (all non-idle tasks stalled simultaneously). The kernel documentation also distinguishes the full stall signal as the severe condition associated with thrashing. The page currently calls the `some` memory metric “Memory Subsystem Thrashing” (`AuditView.jsx:238`) even while separately rendering a `full` value.

**Required fix:** show `PSI unavailable` when no parseable file exists; preserve `some` and `full` as separate series; call `some` “Some-task pressure” and `full` “Full-task pressure”. Do not call `some` alone “thrashing”. CPU PSI `full` is not a normal system-wide signal in the same way as memory/I/O; follow the kernel's resource-specific definitions. The copy should say `Pressure stall time` or `Tasks delayed by CPU contention`, not “hardware starvation”.

### 4.6 Storage totals double-count parent disks and partitions

**Files:** `client/src/views/Details.jsx:205–228, 287–301`; `server/metrics.js:172–194, 247–315`.

The storage detail page sums `size` and `used` across every row returned by the backend. The backend reports raw block devices and mounted filesystems/partitions. Summing a parent device together with its partition rows can count physical capacity multiple times. The “Primary Root Use” card also reads `disks[0]` without selecting the `/` mount (`Details.jsx:227–228` and `291–295`).

**Required fix:** distinguish the data models:

- Physical devices: list whole block devices once; do not sum partitions into a whole-device total.
- Filesystems/mounts: list mount points and calculate totals over unique mount IDs/filesystems.
- Primary root: select `mountpoint === '/'`, not array index 0.
- Show `Not mounted` / `N/A` instead of treating an unmounted device as 0% used.
- Avoid summing bind mounts and duplicate mounts of the same filesystem into a single host capacity total without clear semantics.

### 4.7 Audit polling independently runs stateful metric collectors

**Files:** `AuditView.jsx:10–29`; `server/metrics.js:99–125, 476–512, 784–848`; `server/index.js:57–71, 101–108`.

`/api/audit` calls `getCpuMetrics()` and `getProcessMetrics()` separately from the regular snapshot collector. These functions use module-level baselines (`lastCpuTimes`, `lastProcessCpu`). The normal snapshot collector also calls them. The Audit page polls `/api/audit` every five seconds.

This means the audit request can update CPU/process baseline state between normal snapshot samples, changing the denominator and timing used by the next rate calculation. It also repeats a full process scan on a separate cadence.

**Required fix:** make all sampling happen in one collector pipeline. Cache the most recent sample and calculate an audit from that immutable snapshot. Or separate raw counter reads from pure delta calculation so one endpoint cannot mutate another endpoint's baselines. The audit view should not independently rescan `/proc` every five seconds.

## 5. P1 — Navigation, interaction and component defects

### 5.1 Browser Back/Forward does not synchronize the active view

**File:** `client/src/App.jsx:162–173, 188–194`.

The app listens for `hashchange`, but navigation uses `history.pushState()`. `pushState()` does not emit `hashchange`; Back/Forward navigation emits `popstate`. There is no `popstate` listener.

**Impact:** the URL hash may change when users press Back/Forward while the visible React view stays on the previous page.

**Fix:** either use a router, or listen for `popstate` and `hashchange` and update the view from the current hash. Add one shared navigation function that keeps the URL and view in sync. Prefer real `<a href="#/processes">` navigation links so browser link behavior, copy link and open-in-new-tab work. Use buttons for actions, not route navigation.

### 5.2 “Reconnect” buttons only refresh HTTP snapshot

**Files:** `App.jsx:130, 223–230, 259–279`; `Topbar.jsx:91–100`; `useMetrics.js:71–79, 166–175, 194`.

`useMetrics()` returns `refresh: load`, where `load()` fetches only `/api/snapshot`. The `reconnect()` method actually closes/reopens the WebSocket. But the Topbar retry button and the error banner are passed `refresh`, then labelled `Refresh telemetry stream` / `RECONNECT`.

**Fix:** either rename the button `Refresh snapshot` and explain that the live socket is still down, or pass `reconnect` when the intention is to reconnect the stream. Use independent status for `HTTP snapshot` and `WebSocket stream` if polling can continue while socket is offline.

### 5.3 Mobile drawer inherits desktop collapsed state

**Files:** `Sidebar.jsx:28–31, 122–160`; `components.css:590–606, 675–689, 1271–1290`; `App.jsx:133–135, 199–210`.

The mobile rail receives the persistent desktop `collapsed` value. At widths ≤900px, CSS changes the sidebar to a fixed off-screen drawer, but the `.is-collapsed` class still hides labels/identity text and reduces the rail to the collapsed width. A user who had collapsed the sidebar on desktop may open a mobile drawer that is only an icon strip.

**Fix:** use separate state for desktop collapse and mobile-open; on mobile, always render the full-width labelled drawer. Use `100dvh`, top/bottom safe-area insets, and manage focus/scroll while open.

### 5.4 Drawer is visually modal but not managed as a modal

**Files:** `App.jsx:213–220`; `Sidebar.jsx:28–32`; `components.css:1272–1290`.

The scrim blocks pointer interaction visually, but there is no dialog semantics, focus movement into the drawer, focus trap, background `inert` state, or focus return to the menu button when closed. Escape closes the menu globally, but focus is not restored.

**Fix:** decide whether the drawer is modal. If modal, implement an accessible dialog pattern with initial focus, focus containment, Escape, inert background and return focus. If non-modal, remove the scrim interaction blocking and keep the drawer non-modal. Do not combine a modal visual treatment with non-modal keyboard behavior.

### 5.5 Process detail panel is not an accessible dialog

**File:** `client/src/views/Processes.jsx:270–376`.

The process inspector is an overlay built with ordinary `<div>` elements. It has no `role="dialog"`, `aria-modal`, accessible title relationship, focus management, or Escape handler. It claims `CLOSE [ESC]` but Escape only closes the mobile nav in `App.jsx:162–165`.

**Fix:** use native `<dialog>` or an accessible dialog primitive. On open, move focus into it; trap focus; close on Escape; restore focus to the invoking row/button. Constrain height to viewport and use internal scrolling. Make the process row a real button/link or remove its pointer-click behavior; a clickable `<tr>` is not keyboard-operable.

### 5.6 Collapsed identity uses dangling aria-controls target

**File:** `Sidebar.jsx:63–69, 94–119`.

`aria-controls="identity-details"` points to an element that is only mounted when expanded. Either keep the target mounted and hide it with `hidden`, or make the relationship accurate when expanded. Use `aria-expanded` with a stable controlled region.

### 5.7 Navigation and action semantics

**Files:** `Sidebar.jsx:129–155`; `App.jsx:188–194`.

Every navigation item is a `<button>`. The active button gets `aria-current="page"`, which is a useful cue, but anchor semantics would be better for view navigation. Use buttons for Pause stream, Resume stream, theme, masking and collapse. Use links for destinations.

### 5.8 Error and status feedback

**Files:** `App.jsx:259–280`; `Topbar.jsx:64–77`.

- The error banner uses `role="alert"`, good, but the retry action is miswired as described above.
- `200 LIVE` is misleading: 200 is an HTTP status code, not a WebSocket connection state. Display `LIVE`, `STREAM CONNECTED` or `SNAPSHOT AVAILABLE`.
- The clock is `aria-hidden="true"` (`Topbar.jsx:75`). If it is decorative, leave it decorative; if it conveys operational value, expose a `<time dateTime>` element with an accessible label and locale-aware formatting.
- Distinguish `connected`, `stale`, `polling fallback` and `offline`; do not show a green dot as the only state.

## 6. P1 — Linux telemetry and calculation defects

### 6.1 CPU frequency average includes unavailable zero entries

**File:** `client/src/views/Details.jsx:37–38`.

The calculation divides the total of all frequencies by `freq.length`, even if one or more cores have `0` (unsupported/not readable). This understates the average.

**Fix:** average only finite positive frequencies; show `N/A` if no valid frequency samples exist. Do not show `BASE` when `avgFreq` is zero (`Details.jsx:53`); “base frequency” is a hardware specification that has not been collected.

### 6.2 CPU utilization is called scheduler load/capacity

**Files:** `Overview.jsx:117–124`; `Details.jsx:48–50`; `TelemetryTicker.jsx:19–21`.

The CPU usage value derives from `/proc/stat` counter deltas. The Linux load average comes separately from `/proc/loadavg` (`metrics.js:118–123`). `SCHEDULER LOAD` and `PROCESSOR CAPACITY` blur CPU utilization with load average. A CPU utilization percentage is not the Linux load average.

**Fix:** use `CPU utilization` for the percentage and `Load average (1/5/15 min)` for the three load-average values. Keep `logical CPUs` rather than `cores` unless physical-core topology is independently detected.

### 6.3 CPU delta matching relies on array position

**File:** `server/metrics.js:31–59` (CPU counter comparison helper) and `99–115`.

Counter samples should be matched by the CPU row name (`cpu`, `cpu0`, `cpu1`, …), not array index. A hotplug event or a changed CPU list can misalign the prior and current samples.

**Fix:** store counters in a `Map` keyed by CPU label; if a CPU appears or disappears, report a warm-up / unavailable delta for that CPU rather than calculating against a different CPU.

### 6.4 Frequency rows include inaccessible cores

**File:** `server/metrics.js:61–80`.

The collector returns frequency `0` on read failure. The frontend should not treat this as a real 0 GHz measurement. Prefer explicit `null` plus an `available`/`source` field, and display `N/A`.

### 6.5 Disk device filtering misses common device-mapper and virtual block types

**File:** `server/metrics.js:172–194`.

The name filter covers `sd`, `hd`, `vd`, `nvme`, `mmcblk`, `loop`, and `ram`, but does not reliably include device-mapper (`dm-*`), md RAID (`md*`), zram (`zram*`), Xen (`xvd*`), NBD or other common device names. This can omit root storage on systems using LVM or encrypted mapper devices.

**Fix:** derive block topology from sysfs relationships rather than a short hardcoded prefix list. Present unsupported devices as omitted/unmapped with a diagnostics reason, not silently absent.

### 6.6 Disk and network counter resets can produce negative rates

**Files:** `server/metrics.js:197–228` (disk rates), `318–380` (network counters).

Network byte-rate deltas clamp negative differences to zero, but error/drop counters and some disk latency/counter deltas are not consistently clamped against resets or device removal. Counter reset/hotplug can generate negative spikes.

**Fix:** when a current counter is lower than the previous one, treat it as a reset/new device baseline and return an unavailable/zero rate for that interval. Do not create a negative throughput or latency.

### 6.7 `df` is executed synchronously and its parsing is fragile

**File:** `server/metrics.js:247–287`.

Disk filesystem data is collected using synchronous `df -B1 --output=...` and parsed by splitting whitespace. Long filesystem sources or mountpoints containing spaces can wrap or alter field positions. This runs on the Node event loop every snapshot.

**Fix:** use a robust mountinfo parser plus `statfs`/a maintained library, or run `df -P -B1` through asynchronous `execFile` with a bounded timeout and correct escaping. Cache stable mount topology and refresh it less often than throughput counters.

### 6.8 Device and filesystem identity must be separated

**Files:** `server/metrics.js:271–315`; `Details.jsx:205–228, 287–301`.

The backend attempts to map a mounted filesystem to a block device but its output mixes physical block-device rows with mount-specific values. UI totals then sum these mixed rows. The API shape should distinguish `blockDevices[]` from `filesystems[]` and include stable IDs (major:minor, mount ID, parent device ID).

### 6.9 Network MAC address is included in every snapshot

**File:** `server/metrics.js:358–411`.

`mac` is returned in network interface objects. The UI may not expose it prominently, but `/api/snapshot` and JSON export send it. Treat it as a host identifier and apply the same privacy/export rules as hostname and PID.

### 6.10 Process classification is not threat classification

**Files:** `server/metrics.js:415–512`; `server/metrics.test.js:41–49`; `Processes.jsx` process labels/inspector.

The collector classifies based on UID/root privilege and parent PID characteristics. This is a privilege/account classification, not evidence that a process is malicious or a threat. The field and test currently call it `threatClassification`.

**Fix:** rename to `privilegeClass` or `accountClass` (`kernel-task`, `root`, `user`, `unknown`). Avoid “threat”, “malware”, “suspicious” or “secure” language unless a real detection engine exists and explains its evidence.

### 6.11 Process scan is synchronous and sampled

**File:** `server/metrics.js:476–512`.

The collector traverses numeric `/proc` entries and reads multiple files for each process synchronously, then returns up to 100 CPU-ranked entries. At a 1.2-second polling cadence, this is an expensive O(number of processes) task on the single Node event loop.

**Fix:**

- Separate process inventory refresh (e.g. every 5–15 seconds) from fast CPU/net/disk sampling.
- Use asynchronous reads with concurrency limits, or a bounded worker if the measurements justify it.
- Make top-N sampling explicit in the API: `sampledCount`, `totalSeen`, `limit`, `sortKey`, `sampleTime`.
- Do not label the sample as all running processes.

### 6.12 GPU telemetry reports unknown utilization as zero

**Files:** `server/metrics.js:519–568`; `Details.jsx:364–395`; `Ring3D.jsx`.

The Intel fallback can return `utilization: null`, but `Details.jsx:384` converts that to `0`. `Ring3D` also coerces missing values to zero. This visually tells the user that the GPU is idle when the backend did not measure it.

**Fix:** preserve `null` as unsupported/unavailable; the ring should render `N/A`, not 0%. Use a type-safe metric contract with `value`, `unit`, `status`, `sampledAt` and `source`.

### 6.13 GPU memory units are encoded as assumptions

**File:** `Details.jsx:386–387`; GPU collectors `metrics.js:519–568`.

The UI multiplies `memoryUsed` and `memoryTotal` by `1024 * 1024`, assuming the collector always returns MiB. Normalize at the server boundary and name fields `memoryUsedBytes` / `memoryTotalBytes`. Never make the frontend guess what unit a collector returns.

### 6.14 AMD GPU enumeration may include connector entries

**File:** `server/metrics.js:519–568`.

Enumerating every sysfs entry whose name starts with `card` can include connector subdirectories such as `card0-DP-*`, not just GPU cards. The collector should validate the expected device directory and use `device/` attributes. It should also decide whether multiple GPUs are supported rather than silently reporting only the first one.

### 6.15 Battery capacity can be reported as zero when unreadable

**File:** `server/metrics.js:616–652`.

`capacity` starts at zero, and the condition `if (capacity >= 0)` is always true. If reading the actual capacity fails, a zero-percent battery can be returned as if it was measured.

**Fix:** initialize to `null`; append only if the read value is finite and in the valid range. If the battery exists but capacity is unavailable, return a battery record with `capacity: null` and `status: unavailable`, rather than a fabricated 0%.

### 6.16 Battery empty-state wording makes an unsupported inference

**File:** `Details.jsx:451–463`.

“No battery supply detected” is reasonably descriptive, but the explanation “AC line power or baremetal workstation topology” invents a cause. A desktop, VM, container or laptop with inaccessible battery sysfs may all produce no data.

**Fix:** `No battery telemetry is available from this host. This may mean no battery device is exposed or the agent cannot read it.`

### 6.17 No fan channels does not mean fans are inactive

**File:** `Details.jsx:434–445`.

“No active fan channels reported” suggests fans are not running. Missing hwmon paths, unsupported drivers or permissions can also explain an empty list.

**Fix:** `No readable fan tachometer data was reported.` Provide a diagnostic reason if available.

### 6.18 System metadata invokes shell tools on every collection

**Files:** `server/metrics.js:655–670`; `server/index.js:57–71, 198–205`.

`getSystemInfo()` runs `uname -r`, `lsb_release`/shell pipeline and `grep` through `execSync`. The `getconf` calls at module load are also synchronous, and page-size lookup does not specify a timeout (`metrics.js:6–10`). System metadata is mostly stable and does not need refreshing every 1.2 seconds.

**Fix:** use Node's `os` API and direct `/etc/os-release` parsing; cache kernel/distro/CPU model at startup or refresh on a slow cadence. Every external command must use `execFile`/`spawn` with a fixed executable and argument array, bounded timeout, output size limit and error handling.

### 6.19 The collector error wrapper hides data quality failures

**File:** `server/index.js:46–53, 57–71`.

A collector exception is logged and replaced with `null` or `[]`. The frontend cannot distinguish `no devices` from `collector failed`, or unsupported from permission denied.

**Fix:** return a per-collector diagnostic envelope: `{status:'available'|'unsupported'|'permission-denied'|'error', value, sampledAt, reasonCode}`. Rate-limit repeated warning logs and expose a safe diagnostics view.

## 7. Backend security and exposure model

### 7.1 Loopback default is good, but it is not a complete security boundary

**File:** `server/index.js:24–25, 33–44, 86–112, 136–153`.

The default host is `127.0.0.1`, which is appropriate for a local dashboard. However `HOST` is environment-configurable. `/api/health`, `/api/audit` and `/api/snapshot` have no authentication or authorization middleware. WebSocket origin validation is only in the upgrade handler; an absent Origin is allowed for local scripts.

**Risk:** if the user sets `HOST=0.0.0.0` to access the dashboard from another device, the full host snapshot and audit are exposed to the network unless an external trusted boundary is added. `/api/snapshot` includes sensitive host/process/network details.

**Required product rule:**

- Keep loopback binding as the documented default.
- Put a conspicuous warning in the UI and README when binding to a non-loopback interface.
- Do not recommend `HOST=0.0.0.0` on an untrusted LAN.
- If remote access is a supported product feature, add authentication, authorization, CSRF/origin policy for HTTP, rate limits and transport through a trusted reverse proxy/tunnel.
- Avoid returning host/port config detail in public health endpoints unless required.

### 7.2 WebSocket origin checks do not protect the REST API

**File:** `server/index.js:33–44, 136–153`.

The exact allowlist is applied to WebSocket upgrades only. It should not be described as HTTP API origin protection. CORS is installed as a dependency but not used. A same-origin Vite proxy does not require permissive CORS; keep it that way unless a supported cross-origin client is added.

### 7.3 Shell execution contradicts the README

**Files:** `README.md:26`; `server/metrics.js:6–10, 247–287, 515–568, 657–668, 683–697`.

The README says “no shell execution,” but the code uses `execSync()` for system data and process helpers. The process-control helpers are not currently imported by `server/index.js` and there are no process mutation routes, so this audit does **not** claim they are remotely reachable. They are still risky dormant code and contradict the documentation.

`setCpuAffinity(pid, cores)` (`metrics.js:692–697`) constructs a shell command using string interpolation, does not validate `pid` or `cores`, and has no timeout. It is a latent command-injection hazard if ever exposed. `reniceProcess` and `killProcess` are similarly unused helpers that should either be removed from this read-only product or implemented with strict authorization and fixed argument arrays.

### 7.4 HTTP security headers are a useful start, not a certification

**File:** `server/index.js:74–84`.

Good: `X-Content-Type-Options`, `Referrer-Policy`, `Cross-Origin-Resource-Policy`, `X-Frame-Options`, and `Cache-Control: no-store` for API routes.

Further work:

- Add a carefully tested Content Security Policy for the app's actual asset/font/connect requirements.
- Add `Permissions-Policy` if the app does not need privileged browser capabilities.
- Consider `Cross-Origin-Opener-Policy`/`Cross-Origin-Embedder-Policy` only where the application requires them; do not add headers blindly.
- Add authentication and request limits before allowing non-loopback binding.
- Do not use “LOOPBACK HARDENED” in the UI if the host binding can be changed by configuration.

### 7.5 WebSocket message size limit is unnecessarily large for a one-way telemetry stream

**File:** `server/index.js:132–134`.

The server sends snapshots and has no evident need to accept 4 MB client messages. Reduce `maxPayload` or reject client frames if the protocol is strictly server-to-client. Keep heartbeat and buffered-send protection; those are positive design choices.

## 8. UI visual system and design psychology

### 8.1 The identity is clear; its application is too uniform

**Files:** `tokens.css:6–128`; `components.css:102–175, 230–240, 280–325, 1110–1129`.

The Field Dossier concept is cohesive: ivory paper, espresso ink, oxblood red, antique brass/clay, black AMOLED mode, mono metadata, Bricolage masthead, hard offset shadows and evidence-like stamps. This is a recognizable design direction.

The problem is that almost every panel uses a strong border, a hard offset shadow and an uppercase stamp. When all cards have the same elevation and most section headers look like status labels, users cannot quickly distinguish:

- primary task / main insight;
- supporting metric;
- diagnostic evidence;
- action / control;
- neutral metadata;
- warning / alert.

**Psychological effect:** the interface feels intense and “classified” everywhere, so the genuinely important warning becomes less distinctive. The visual vocabulary stops communicating hierarchy and becomes decoration.

**Fix: establish 3 explicit surface tiers.**

| Tier | Use | Suggested treatment |
|---|---|---|
| Primary / hero | Main overview, current posture, primary action | 2.5px outline, hero shadow, stronger type scale |
| Data card | CPU, memory, network, device cards | 1.5px outline, 3px shadow or no shadow, medium radius |
| Inset / evidence | Supporting rows, code values, secondary details | 1px rule, recessed paper surface, no large shadow |

Keep the tactile look, but don't put every data block on the same “raised plate.” Use the 3px/6px/9px shadow tokens intentionally, not everywhere.

### 8.2 Stamps are overloaded

**Files:** `components.css:138–175`; `AuditView.jsx:70–71, 96–98, 117–123`; `Sidebar.jsx:147–153`; `Overview.jsx:64–70`.

`stamp--confirmed` and `stamp--live` are styled identically (`components.css:154–158`). The UI uses `CONFIRMED NODE`, `HARDENED`, `SEC`, `KERNEL 4.20+ PSI`, `TIMESERIES` and other tags in nearly identical treatment. `confirmed` implies evidence has been validated; a descriptive section badge is not a confirmed state.

**Fix:** make neutral metadata a neutral tag; reserve green/amber/red for actual status. Distinguish `live` (connected), `warning`, `critical`, `unknown`, `unsupported`, `source` and `category`. Never use `confirmed` for ordinary page labels.

### 8.3 Status color semantics are inconsistent

Red is both the brand/action color and a “live/confirmed” status. The dot is green in light mode and cyan in dark mode, while `stamp--live` is red. A red “live” badge often reads as alert/error; a green/cyan dot reads healthy. This is not automatically wrong, but it needs a deliberate semantic color map and text labels.

**Fix:** brand red for primary actions and selected emphasis; green/cyan for healthy/connected; amber for warning/degraded; red for destructive/critical; neutral grey for unknown/metadata. The words must carry status as well as the color.

### 8.4 Too many uppercase labels create visual noise

**Files:** `components.css:104–112, 138–152, 770–795`; broadly throughout `Overview.jsx`, `AuditView.jsx`, `Details.jsx` and `Processes.jsx`.

Uppercase mono labels reinforce the dossier theme, but the project applies the treatment to too many items: card labels, controls, metric descriptions, table headings, status labels and explanatory text. This reduces scannability and causes long labels to consume horizontal space on mobile.

**Fix:**

- Use sentence case for explanatory labels, buttons and empty-state messages.
- Keep uppercase mono for short IDs, telemetry keys, timestamps and small dossier metadata.
- Use sentence-case human labels for core metrics: `CPU utilization`, `Available memory`, `Disk read rate`.
- Avoid technical theater in user-facing wording; a technical dashboard can be precise without making every sentence look like a command-line log.

### 8.5 Card repetition dilutes information hierarchy

**Files:** `components.css` `.card`, `.card--fold`, `.proof`; `Overview.jsx`, `Details.jsx`, `AuditView.jsx`.

Many page sections repeat the same recipe: title, stamp, note, large bordered rectangle, inset rectangle, same shadow. This gives the page a consistent visual grammar but not a strong reading order.

**Fix:** each view should have one main question and one dominant answer. Example:

- Overview: “What is the host doing right now?” Primary four summary metrics, then CPU/memory/storage/network evidence.
- Audit: “What can be observed, and what is unavailable?” Separate heuristic score from raw checks and show source/coverage.
- Processes: “Which sampled processes need attention?” Summary count, filter controls, top-N table and accessible detail drawer.
- Storage: “Which filesystems are full?” Filesystem summary separately from physical device I/O.

Reduce duplicate proof strips when the same numbers already appear in Stat cards immediately below them.

### 8.6 Hero motion competes with the actual job of the dashboard

**File:** `DossierHeroTitle.jsx:18–80, 82–129, 141–159`.

The pointer tilt and glyph lift are visually expressive. But the hero title is not the user's primary task after the first visit. Keep motion subtle and local; do not make every telemetry value or every section animate. The current implementation does a large amount of work on every pointer movement (see animation audit below).

## 9. Typography, sizing, contrast and units

### 9.1 Typography choices are good; scale is too small for metadata

**Files:** `main.jsx:1–9`; `tokens.css:68–71`; `components.css:32, 104–112, 138–152, 770–795, 1221–1228`.

Font imports are appropriate:

- Bricolage Grotesque: display and hero.
- Space Grotesk: general body copy.
- IBM Plex Mono: instrumentation and tabular values.

However:

- body is set to 15px (`components.css:32`); use 16px as the baseline for the main UI.
- `.lbl` is 0.68rem (~10.9px at 16px), `.stamp` 0.66rem (~10.6px), navigation text 0.78rem (~12.5px), and many notes use 0.82–0.84rem (~13.1–13.4px).
- the search input is 0.8rem (~12.8px), below the 16px mobile input size recommended by Vercel's guidelines to avoid iOS Safari zoom behavior.

**Fix:** reserve 10–11px only for nonessential micro metadata; raise primary labels and helper text to 12–14px and body to 16px. Inputs should be at least 16px on mobile. Allow users to zoom; do not lock page scale.

### 9.2 Font package drift

**Files:** `main.jsx:3–6`; `client/package.json`.

`@fontsource-variable/instrument-sans` is declared but not imported/used. `recharts` and Tailwind packages are also declared but the visible implementation uses handcrafted SVG/plain CSS, not Recharts/Tailwind. Remove unused dependencies only after searching the complete source and verifying no runtime import/build plugin consumes them. This is bundle hygiene, not a blocker by itself.

### 9.3 Contrast check — two light-theme pairs miss AA slightly

Computed with the WCAG relative luminance formula from the colors in `tokens.css`:

| Foreground | Background | Contrast | Result for normal text |
|---|---|---:|---|
| `#756A57` (`--ink-mute`) | `#F1EBDC` (`--paper`) | **4.46:1** | Slight fail vs 4.5:1 |
| `#756A57` (`--ink-mute`) | `#F9F5EA` (`--paper-3`) | **4.87:1** | Pass |
| `#B23A2C` (`--red-active`) | `#F1DBCF` (`--red-active-tint`) | **4.46:1** | Slight fail vs 4.5:1 |
| `#14120F` (clay CTA text) | `#FF8267` (gradient top) | **7.69:1** | Pass at top |
| `#14120F` (clay CTA text) | `#C93325` (gradient bottom) | **3.55:1** | Fail for normal-size text at bottom |

**Fix:** adjust muted text and red-active pair slightly darker or lighter, and revise the lacquer CTA gradient/text pair so the lowest-contrast part still passes 4.5:1 for ordinary button text. Recalculate the full gradient at multiple stops, not only endpoints, and use a contrast checker on rendered states. Large bold text can use the 3:1 threshold, but button labels here are not consistently large enough to rely on that exception.

### 9.4 Color semantics and dark mode

**File:** `tokens.css:6–128, 134–214`.

The light/dark palette is intentional and dark tokens are centralized. Good. Remaining concerns:

- `--clay-btn-hi` and `--clay-btn-lo` remain fixed in dark theme, so the bright red lacquer treatment may be stronger than the dark theme's otherwise restrained palette.
- the same `--red-active` semantic role is used for both live and confirmed statuses.
- shadow `--ink` is a full-strength color; strong shadows on every card produce a heavy page at low brightness.
- the `--ink-mute` comment claims 4.5:1 but its actual contrast on base `--paper` is 4.46:1.

**Fix:** document color roles (`brand`, `interactive`, `success`, `warning`, `danger`, `unknown`, `surface`, `border`) and validate each foreground/background pairing for both themes.

### 9.5 MB, MiB, GB and GiB — current formatter is mostly correct

**File:** `client/src/lib/format.js:8–18`.

`bytes()` divides by 1024 and emits `KiB`, `MiB`, `GiB`, `TiB`, `PiB`. That is the IEC binary convention and is internally consistent. Do not rename these binary units to `KB`, `MB` or `GB` if the value is still divided by 1024.

Correct conventions:

- `kB`, `MB`, `GB`: decimal multiples of 1000.
- `KiB`, `MiB`, `GiB`: binary multiples of 1024.
- Include a space between value and unit: `12.4 GiB`, not `12.4GiB`.
- For throughput use `MiB/s` or `MB/s` consistently, according to the same base.

**Potential bug:** `bytes()` clamps negative values to zero (`format.js:10`). This is acceptable for an actual byte count but can mask a counter-reset defect in an upstream rate calculation. Counter reset should be handled before formatting.

### 9.6 Missing values are often formatted as numeric zero

**File:** `format.js:34–42`; many consumers in `Overview.jsx`, `Details.jsx`, `AuditView.jsx`, `TelemetryTicker.jsx`.

`clampPct(undefined)` returns 0. `lastOf()` defaults to zero. Multiple views also use `|| 0`. This creates “0% CPU”, “0% GPU”, “0 PSI” and “0% battery” states when a measurement is actually unavailable.

**Fix:** retain `null` and format it as `—` / `N/A`; only clamp a valid numeric value. `0` must mean the sensor actually measured zero.

### 9.7 Labels that need correction

| Current wording | Why it is wrong / unclear | Preferred wording |
|---|---|---|
| `CONFIRMED SECURE` | A heuristic host score cannot prove overall security. | `Heuristic posture score` |
| `HARDENED` | No full hardening baseline is evaluated. | `Checks collected` or remove |
| `CRYPTographically adequate for TLS` | Entropy-available count is not a TLS security certification. | `Kernel entropy availability: N bits` |
| `ENTROPY POOL (BITS)` | Can imply a direct cryptographic assurance measure. | `Entropy availability (bits)` |
| `BAREMETAL` | A failed container check does not prove bare metal. | `Container status unknown/not detected` |
| `DAC ONLY` | AppArmor/SELinux absence detection may be incomplete or inaccessible. | `No LSM detected` only if confidently detected; otherwise `Unknown` |
| `Memory Subsystem Thrashing` for `some` PSI | `some` means some tasks stall; it is not the `full` PSI thrashing condition. | `Memory pressure — some tasks stalled` |
| `Hardware starvation` | PSI measures task stalls/pressure, not literal hardware starvation. | `Resource pressure / stall time` |
| `Committed RSS` | `MemTotal - MemAvailable` is not RSS nor Committed_AS. | `Estimated RAM used` |
| `RAM COMMITTED` | Wrong memory metric. | `Estimated RAM used` |
| `SCHEDULER LOAD` for CPU percent | Confuses CPU utilization with load average. | `CPU utilization` |
| `PROCESSOR CAPACITY` | Percent is utilization, not CPU capacity. | `CPU utilization` |
| `CORES` for `os.cpus().length` | This usually counts logical CPUs, not physical cores. | `Logical CPUs` |
| `200 LIVE` / `200 STREAMING` | HTTP status is not a socket state. | `Live stream` / `WebSocket connected` |
| `NO BATTERY ... AC line power or baremetal workstation` | Cause is not known. | `No battery telemetry is available from this host.` |
| `No active fan channels` | Sensor data might be unavailable rather than fans inactive. | `No readable fan tachometer data was reported.` |
| `Threat classification` | Current classification is privilege/UID/PPID-based. | `Privilege class` |
| `Active interfaces` (if all non-loopback interfaces) | Interface existence does not prove link is active. | `Non-loopback interfaces discovered` |

## 10. Icons, charts and data visualization

### 10.1 Icon system is coherent but fallback hides mistakes

**File:** `client/src/components/Icon.jsx:3–7, 8–121, 123–139`.

The custom SVG icon set has a consistent 24-unit grid, 1.6 stroke and round joins. Decorative icons are correctly marked `aria-hidden="true"` and `focusable="false"` at the SVG root.

However, unknown names silently fall back to `ICONS.server` (`Icon.jsx:138`). This can make an incorrect icon key appear to work while the wrong icon is drawn.

**Fix:** warn in development or throw in tests when an unknown icon name is requested. Add a test that checks every icon name referenced in `App.jsx` and the views exists in the `ICONS` map. Keep icon-only buttons labelled; do not make an SVG the only source of meaning.

### 10.2 Some icons need semantic reassessment

`App.jsx:27` uses the `sensors` icon for Security & PSI Audit. Use a shield/check or audit-document metaphor if one is added to the custom set. The icon must reinforce the destination, not be reused simply because it looks technical. Existing text labels are helpful, so this is lower severity.

### 10.3 Ring3D should distinguish unknown from zero

**Files:** `client/src/views/Details.jsx:364–395, 451–477`; `Ring3D.jsx`.

`Ring3D` receives zero for unsupported GPU utilization and battery capacity fallback. Render an empty ring plus `N/A` for missing values. A true zero should render a zero value with an explicit measured status. A ring itself should not imply a percentage if the source does not provide one.

### 10.4 IsoBars/Sparkline data states

Review the handcrafted SVG charts for:

- accessible title/description;
- a nearby numeric equivalent for every visual trend;
- axis/time range and units;
- color-blind-safe distinctions;
- empty data state vs zero-value data;
- no misleading interpolation over gaps;
- stable viewBox sizing on small screens;
- tabular numeric display where values are compared.

The current charts have accessible labels in some call sites, which is good; verify every chart instance has a useful label. Never rely on red/green alone to communicate a telemetry severity.

### 10.5 Overview headings have broken `aria-labelledby` references

**File:** `Overview.jsx:10–26` defines `CardHead` without an `id` prop; the view uses `aria-labelledby` names for section IDs but the `h2` does not receive those IDs. The referenced heading IDs are therefore not present.

**Fix:** add `id` to `CardHead` and pass it to the rendered heading, or remove the invalid `aria-labelledby` and use `aria-label` only when necessary.

## 11. Animation and motion audit

### 11.1 Hero glitch effect restarts on every render

**File:** `DossierHeroTitle.jsx:16, 82–129`.

`const letters = text.split('')` creates a new array on every render. The glitch effect depends on `[letters]`. The pointer effect also updates `rx`, `ry` and `nearMap`, causing renders. Each render creates a new `letters` array, so the glitch effect cleanup/reinitialization is triggered repeatedly. Its interval and initial delay can be cancelled before the scramble completes.

**Fix:** memoize `letters` with `useMemo(() => text.split(''), [text])`, or move the split into the effect. Store every timeout/interval in refs and clear nested timeouts as well. The effect should depend on stable values only.

### 11.2 Pointer animation causes React state updates at frame rate

**File:** `DossierHeroTitle.jsx:18–80`.

A global `window.mousemove` handler schedules `requestAnimationFrame`, reads the hero rectangle and every glyph rectangle, then performs three state updates (`rx`, `ry`, `nearMap`). This may create React rerenders at ~60 FPS, plus repeated layout reads.

**Fix:** attach pointer listeners to the hero only; measure once per pointer frame or use normalized pointer coordinates from the hero rectangle; write CSS custom properties to a ref element directly for the transform; avoid state updates for every frame. Use CSS transforms/opacity and reduce `getBoundingClientRect()` reads. Reset on `pointerleave` of the hero, not only when the entire document is left.

### 11.3 Glitch content is announced as changing heading text

**File:** `DossierHeroTitle.jsx:141–159`.

Screen readers can receive Katakana/random glyph changes as part of the H1. Keep the accessible heading stable (`BLINK // HOST DOSSIER`) and put animated visual glyph spans inside `aria-hidden="true"`, with a stable visually-hidden text label.

### 11.4 Reduced-motion handling is incomplete

**Files:** `DossierHeroTitle.jsx:18–22, 82–85`; `components.css:18–26`; `App.jsx:188–194`.

The hero JS checks `prefers-reduced-motion`, which is positive. CSS uses an extremely short animation duration and one iteration, but the ticker still runs through an accelerated cycle rather than becoming static. `window.scrollTo({behavior:'smooth'})` is explicit JavaScript smooth motion and is not guarded by the preference.

**Fix:** in reduced motion, disable nonessential animations (`animation: none !important; transition: none !important`) or replace them with static states; do not accelerate an infinite marquee into a one-frame cycle. Guard smooth scrolling in JS with `matchMedia` and default to instant scroll for reduced-motion users. Re-evaluate motion if the preference changes at runtime.

### 11.5 Ticker only pauses on mouse hover

**Files:** `TelemetryTicker.jsx:39–45`; `components.css:463–487`.

Ticker moves forever for 45 seconds and pauses only when hovered. There is no keyboard-accessible Pause/Resume control. W3C WCAG 2.2.2 calls for a mechanism to pause, stop or hide automatically moving information that starts and continues for more than five seconds alongside other content, subject to the criterion's exceptions.

**Fix:** add a visible, keyboard-operable pause button; honor reduced motion by defaulting to static content; consider a non-animated strip with an explicit update timestamp. Ensure the control stops motion even when focus is inside the ticker.

### 11.6 `transition: all` is avoidable

**Files:** `components.css:186, 795, 846, 1247` (and any other grep matches).

Replace `transition: all` with explicit properties such as `background-color`, `color`, `transform`, `box-shadow`, `opacity`. Animating all properties can cause unnecessary paint/layout work and unexpected transitions.

### 11.7 Animation hierarchy recommendation

- Hero tilt/glitch: optional, low amplitude, desktop fine-pointer only.
- Buttons: short transform/shadow press feedback (existing idea is good).
- Sidebar/drawer: transform rather than animating `left`; disable with reduced motion.
- Telemetry values: do not animate every incoming number; use subtle change highlight only if it helps identify updated data.
- Ticker: static by default on mobile or reduced-motion preference; explicit pause.
- Charts: update data without large spring/scale movement.

## 12. Responsive layout and touch ergonomics

### 12.1 Topbar lacks a compact mobile composition

**Files:** `Topbar.jsx:34–100`; `components.css:868–923, 1271–1297`.

The Topbar uses a single flex row with breadcrumb, mask toggle, live badge, clock, theme toggle and refresh. The mobile media query only moves the sidebar and shows the menu button; it does not reflow or simplify the Topbar. At narrow widths, the right-side controls and long breadcrumb compete for width and may be clipped because the page uses `overflow-x: hidden` at the body level.

**Fix:** create a two-row or compact mobile topbar. Keep the current page title and menu visible; move clock and secondary status into a compact overflow/control group; preserve theme and mask actions. Do not hide overflow as a substitute for responsive design.

### 12.2 Touch targets

**Files:** `components.css:633–641` (28px collapse button), `890–899` (36px icon buttons), `Sidebar.jsx` (small nav items), `Topbar.jsx:52` (34px redaction button).

The W3C WCAG 2.2 AA minimum target-size criterion is 24×24 CSS pixels with exceptions; Vercel's web-interface guidance recommends 44px on mobile as a stronger touch target. This UI uses some 28–36px controls. They may meet the minimum criterion, but they are less forgiving on touch devices, particularly when close together.

**Fix:** aim for 44×44px interactive hit areas on mobile; where the visual control stays small, expand its invisible hit target and ensure neighboring targets have enough spacing. Keep the visual Field Dossier style while improving the actual target box.

### 12.3 Input font size on mobile

**File:** `components.css:1221–1228` uses `.8rem` (~12.8px) for search. Set at least 16px on mobile to avoid Safari focus zoom/pan and improve readability.

### 12.4 Safe areas and dynamic viewport

**Files:** `components.css:583–606, 1272–1290`.

Sidebar uses `100vh` and mobile drawer positioning but does not account for `env(safe-area-inset-top/right/bottom/left)`. Use `100dvh` with fallback; pad the mobile drawer and topbar with safe-area insets. Test browser chrome expansion, notches and landscape orientation.

### 12.5 Grid responsiveness

`grid-2` collapses to one column at 960px (`components.css:1095–1107`), which is a sensible baseline. Still verify the dense table and multi-column proof strips at 320, 360, 390, 768, 1024 and 1440 CSS pixels. Verify zoom 200% and text scaling. A 960px breakpoint may collapse too early for some tablet landscape widths, while card minimum widths can cause overflow inside nested grids.

### 12.6 `overflow-x: hidden` conceals layout defects

**File:** `components.css:32–36`.

The body hides horizontal overflow. This can conceal clipped content rather than fix its source, especially the Topbar and long identifiers. Remove the global suppression after fixing each component's intrinsic width, `min-width`, wrapping and overflow behavior. Keep horizontal scrolling only for genuinely tabular content with a visible scroll affordance.

## 13. View-by-view audit

### 13.1 Overview (`client/src/views/Overview.jsx`)

**Strengths:** a clear hero statement, primary actions, summary metrics, and a disk-selection attempt that prefers `/` (`Overview.jsx:32–45`). The hero visually establishes identity and the three actions provide a useful next step.

**Issues:**

- `clampPct()` maps missing CPU/memory metrics to 0 (`format.js:34`; `Overview.jsx:39–40`). Initial loading therefore looks like a genuinely idle system.
- `CardHead` cannot forward heading IDs (`Overview.jsx:10–26`), but some sections reference heading IDs through `aria-labelledby`.
- `PROCESSOR CAPACITY` should be `CPU utilization` (`Overview.jsx:117–120`).
- Export downloads the unfiltered raw `metrics` object (`Overview.jsx:98–112`), bypassing visible redaction.
- `LIVE TELEMETRY`, `CONFIRMED NODE`, `HOST` and status stamps appear together (`Overview.jsx:63–70`), creating too much badge noise. `CONFIRMED NODE` is not a useful host state.
- The hero subtitle says “zero external charting bloat”, but Recharts is in the package dependencies. The library is not imported in the current source, so the phrase is confusing; either remove unused dependency or make the claim exact.
- The data summary is followed by a Stat row with similar data. Verify that both summary strips answer different questions rather than repeat values.

**Fix order:** data states → safe export → correct labels → heading IDs → reduce duplicate badge/metric repetition.

### 13.2 Security & PSI Audit (`client/src/views/AuditView.jsx`)

This is the highest-risk UI because it looks authoritative. Apply all P0 points in section 4. Additional issues:

- `fetchAudit()` silently ignores HTTP non-2xx responses (`AuditView.jsx:10–23`). `catch` only catches network/JSON exceptions; no user-facing error state is set for 401/403/404/500.
- The page polls every five seconds (`AuditView.jsx:25–29`) and triggers expensive independent scans.
- ASLR meters always show the first two segments as on (`AuditView.jsx:103–107`), even when a valid lower ASLR level is reported.
- Isolation meter always shows all three segments on (`AuditView.jsx:145–149`), regardless of actual telemetry.
- `!sec.appArmor` and `!sec.selinux` returns `DAC ONLY` (`AuditView.jsx:159–168`), but a false result can mean unknown or not mounted.
- Missing PSI reports `NOMINAL` (`AuditView.jsx:197–200, 238–240, 276–277`).
- The page calls `some` PSI “Memory Subsystem Thrashing” (`AuditView.jsx:238–240`), which overstates the measurement.
- `loading` only disables Run Audit; no skeleton or error panel identifies initial state.

**Fix order:** false status removal → tri-state metrics → endpoint errors → pure audit from cached sample → correct PSI semantics → meter logic.

### 13.3 Processes (`client/src/views/Processes.jsx`)

**Strengths:** local search/filter/sort controls and `aria-pressed` on segmented options are good interaction foundations. The server returns a bounded list, which protects the page from an unlimited table.

**Issues:**

- Row-level click behavior is not keyboard-operable on the `<tr>`; the detail button is keyboard accessible, but the row itself should not pretend to be an interactive control.
- The inspector says `CLOSE [ESC]` but the app has no Escape handler for it.
- Inspector is not an accessible dialog and does not manage focus.
- It displays details such as UID, PPID, PID and affinity, while PID masking is only applied in certain table cells. Decide which fields are sensitive and apply a consistent privacy policy.
- Backend list is CPU-ranked top 100 (`metrics.js:476–512`); UI wording should say “Top 100 sampled processes” and show `100 of N` if total process count is available.
- “Threat classification” should be `Privilege class` or `Process type` because the logic is not threat detection.
- On narrow screens, long affinity strings/process names and the modal body need overflow handling.

**Fix order:** accurate sample scope → semantic table actions → dialog accessibility → privacy display → long-string handling.

### 13.4 CPU (`client/src/views/Details.jsx:31–123`)

- Average CPU frequency includes zero/unavailable records (`Details.jsx:37–38`).
- `SCHEDULER LOAD` describes CPU utilisation but not Linux load average (`Details.jsx:48–50`).
- Missing frequency shows `BASE` (`Details.jsx:53`), an invented hardware spec.
- `cores.length || 1` shows at least one logical core even when core data is unavailable (`Details.jsx:45`). Use unknown state.
- Per-core display is sliced to 16 (`Details.jsx:72`); show `Showing 16 of N logical CPUs` and allow expansion/scroll for larger hosts.
- The chart and proof strips should state whether the sampling interval is 1.2 seconds and show last sample time.

### 13.5 Memory (`client/src/views/Details.jsx:125–203`)

- Rename `Committed / Used`, `Committed RSS`, `RAM Commitment` to accurate memory terms.
- The explanatory note at `Details.jsx:196` says “Process RSS represents task page table allocation.” RSS is resident set size, not page-table allocation. Page tables are separately accounted for in `/proc/meminfo` (e.g. `PageTables`).
- `VIRTUAL VM` stamp (`Details.jsx:154`) is not supported by the data; remove it or use a factual source label such as `MEMINFO`.
- `No swap device active` is a reasonable short state, but make clear if zram/zswap are separate mechanisms.
- Missing memory sample becomes 0% (`Details.jsx:126–127`) rather than loading/unavailable.

### 13.6 Storage (`Details.jsx:205–307`)

- Double-counted physical device/partition capacities in totals.
- `disks[0]` is not guaranteed to be the root filesystem.
- No mount / no mapped filesystem may display 0% used.
- Device list and filesystem usage must not be aggregated in one denominator.
- Latency and rate fields should be `N/A` until two valid samples are available.
- Keep device rows horizontally scrollable on mobile, but add visible scroll affordance and an accessible summary.

### 13.7 Network (`Details.jsx:309–363`)

- Sum of RX/TX across every non-loopback interface can double-count when bridges/veth/tunnels represent the same traffic path. Explain that it is a sum of interface counters, not guaranteed unique physical traffic.
- The backend includes MAC addresses; do not show/export without user intent.
- “Active” should not be used unless the interface's operational state is read and surfaced.
- Provide separate interface state (up/down/unknown), address privacy policy and timestamp.

### 13.8 Graphics (`Details.jsx:364–395`)

- Unknown Intel utilization becomes 0%.
- Memory unit assumption is in frontend rather than server contract.
- Empty state says accelerated GPU telemetry is not reported, which is better than “no GPU exists”; keep driver permission and unsupported states explicit.
- Multiple adapters should have stable IDs and each chart should name the adapter, not only “GPU utilisation”.

### 13.9 Sensors (`Details.jsx:397–449`)

- Empty state says “Board firmware does not expose…” but the code can only say that the current readable `hwmon` scan returned no channels. Driver/permissions/kernel config are possible causes.
- “No active fan channels” is not the same as “fan stopped.”
- Sensor thresholds 70°C/85°C are generic and may not apply to every sensor. Use per-sensor labels/source and mark the color scale as a generic attention indicator, not a validated thermal limit.

### 13.10 Battery (`Details.jsx:451–489`)

- Backend's zero default can create a false 0% battery; fix source contract first.
- “No battery means AC line power or baremetal” is an unsupported inference.
- `capacity || 0` makes `null`/missing render zero (`Details.jsx:471–476`). Keep unknown distinct from zero.
- Time-to-full is collected in backend but not displayed; if shown, avoid extreme/negative values and label as estimate.

## 14. React state, lifecycle and frontend data flow

### 14.1 Polling runs even when WebSocket is connected

**File:** `client/src/hooks/useMetrics.js:3–5, 71–79, 147–164`.

The comment describes polling as fallback, but `setInterval(load, 5000)` starts unconditionally even when the WebSocket is connected. That causes duplicate API requests and can race with the WebSocket updates. It also means a successful HTTP poll calls `setError(null)` (`ingest`, lines 67–69), potentially clearing the error while WebSocket remains disconnected.

**Fix:** either poll only while socket is disconnected or explain a deliberate hybrid model. If hybrid, use different state for WebSocket connection and HTTP snapshot freshness. Do not let successful polling clear a stream error without updating the status label.

### 14.2 Reconnect semantics

`reconnect()` clears the current interval before making a new one (`useMetrics.js:166–175`), which is a good protection against stacked pollers. Keep that behavior. However `connect(true)` bypasses the missing-WebSocket branch; validate that WebSocket support exists before forcing a connection. On explicit reconnect, cancel or guard stale in-flight `load()` requests with an AbortController or request sequence ID.

### 14.3 Retry backoff has no jitter

`useMetrics.js:140–142` uses exponential backoff capped at 15 seconds. This is okay for one local agent. Add jitter if many clients can connect to the same shared agent, to avoid synchronized retries. It is lower priority for strictly local use.

### 14.4 History values and duplicate samples

`useMetrics.js:31–65` uses timestamps to dedupe history. The code only checks equality with the last sample, which is sufficient for a single ordered stream but should be revisited if REST and WS can deliver stale snapshots out of order. Reject older timestamps or preserve latest-only ordering.

## 15. CSS and component architecture cleanup

### 15.1 Plain CSS and Tailwind coexist without visible Tailwind usage

**Files:** `client/package.json`, `client/tailwind.config.js`, `client/postcss.config.js`, `client/src/tokens.css`, `client/src/components.css`.

The implementation uses a large custom stylesheet and CSS variables. There are no apparent Tailwind utility classes or `@tailwind` directives in the core stylesheets. Tailwind packages/config may be leftover. Search the full codebase and remove unused packages/config only after verification.

### 15.2 Inline styles bypass the token system

**Files:** `Overview.jsx`, `AuditView.jsx`, `Details.jsx`, `App.jsx` and components.

Inline styles are used for spacing, font sizes, colors, chart dimensions and border colors. Several raw hex colors appear in CSS (`#14120F`) rather than semantic tokens. This weakens consistency and makes dark-mode adjustments harder.

**Fix:** move repeated style decisions into semantic classes/tokens. Keep inline styles for genuinely data-driven values only (e.g. bar width from usage) and avoid duplicating layout/color definitions inline.

### 15.3 Global `transition: all`

Replace every occurrence (found in `.redact`, `.nav-item`, `.foot-action`, `.segmented button`) with explicit transitionable properties.

### 15.4 The custom component APIs should express real states

Suggested contracts:

- `MetricValue`: `value`, `unit`, `status`, `sampledAt`, `source`, `format`.
- `StatusBadge`: variants `healthy`, `warning`, `critical`, `unknown`, `unsupported`, `live`.
- `EmptyState`: `title`, `description`, `reason`, `action`.
- `RedactedValue`: `value`, `masked`, `label`, `sensitiveType`; mask state cannot be overridden globally.
- `DataCard`: `level="primary|standard|inset"`, not arbitrary class strings.
- `ChartFrame`: `title`, `description`, `timeRange`, `unit`, `empty`, `status`.

This gives the product a consistent information model, not just consistent colors.

## 16. README and product claim accuracy

**File:** `README.md:1–90`.

The README is visually and conceptually well aligned with the product, but several operational claims need correction:

- `README.md:26` says strictly loopback-bound; actual host can be changed via `HOST` (`server/index.js:24–25`).
- It says exact allowed browser Origin checking; only WebSocket upgrade is checked (`server/index.js:136–153`), and missing Origin is accepted.
- It says “no shell execution”; code uses `execSync()` (`metrics.js:6–10, 247–287, 515–568, 657–668, 683–697`).
- It says “no unauthenticated external network exposure”; this is only true if it remains bound to loopback or another trusted access boundary is configured. There is no auth on the REST routes.
- “Security & Kernel Isolation Telemetry” should not imply full security validation; current checks are a limited set of readable kernel settings.
- `README.md:25` says zero dependency SVG visualization, but the package includes Recharts. It appears unused in source; either remove the dependency or describe the current rendering accurately.
- The `server` build script is a no-op (`server/package.json`), so `npm run build` does not compile or validate backend code.
- Requirements line `README.md:32` says Linux kernel 4.20+ for PSI and procfs. Procfs exists on far older kernels; PSI is the feature with kernel/config requirements. State requirements per feature and mention `CONFIG_PSI`/permission availability.

**Required fix:** revise security language to state exactly which interface is exposed by default, what happens when HOST is changed, which routes are unauthenticated, and which collectors execute system commands. Avoid phrases such as “hardened”, “confirmed secure” and “cryptographically adequate” until there is a validated control set and threat model.

## 19. Suggested implementation snippets (illustrative, not drop-in complete)

### 19.1 Unknown is not zero

```js
export const clampPct = (value) => {
  if (!isNum(value)) return null;
  return Math.max(0, Math.min(100, Number(value)));
};
```

Render separately:

```jsx
const usage = clampPct(metric?.usagePercent);
return usage == null ? <span aria-label="Unavailable">—</span> : <span>{usage.toFixed(0)}%</span>;
```

### 19.2 Never default the security score to 95

```js
const hasAudit = Number.isFinite(audit?.score);
const scoreLabel = hasAudit ? `${audit.score}/100` : '—';
const posture = hasAudit ? audit.postureGrade : 'Awaiting audit data';
```

This still needs explicit `loading`, `error`, stale and coverage states; the snippet only illustrates removal of the false positive default.

### 19.3 Make global mask authoritative

The simplest safe UI contract is to derive visible state from the global mode and a local reveal that is reset whenever global mode returns to masked. For stronger consistency, move reveal state into context and clear all reveals on global-mask activation. The API and export must still remain protected separately; DOM masking is not a security boundary.

### 19.4 Keep navigation state in one source of truth

Prefer a router with hash history or real URL routes. If retaining hash routing, listen to `popstate`, update React state on navigation, and test Back/Forward. Do not rely on `hashchange` after `pushState`.

### 19.5 Keep audit pure

`getHostAudit(snapshot)` should be a pure function that only reads an immutable snapshot. It should not call `getCpuMetrics()` or `getProcessMetrics()` and mutate their sample baselines. The scheduler/collector should own sampling and call the audit function against the cached result.

## 21. Final verdict

Blink has a product identity worth keeping. The Field Dossier aesthetic is not the problem; it is one of the project's strongest assets. The problem is the distance between the certainty of the interface and the certainty of the data.

A host monitor must be conservative with claims. `Unknown` must look unknown. `0` must mean measured zero. A heuristic score must not be called security confirmation. A visual redaction must not be sold as privacy. A sampled top-100 process list must not imply a complete process inventory. A `some` PSI result must not be described as `full`-stall thrashing.

**Recommended order:** repair data semantics and privacy first, backend sampling second, interaction and accessibility third, then finish the visual hierarchy. Do not spend time adding more animations, shadows or decorative stamps until the product reports its underlying Linux data truthfully.

**Current release recommendation: Prototype only — not production validated.**
